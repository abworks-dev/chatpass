# 重启后的账号授权与刷新恢复

ChatPass 的账号凭据持久化到数据目录中的加密状态，默认 Windows 数据目录是 `%LOCALAPPDATA%\ChatPass`，主密钥保存在当前 Windows 用户的系统安全存储中。正常重启不会清除账号授权。本地管理页面的会话则只保存在进程内存中：重启后请使用启动窗口给出的新管理链接；这与重新连接 ChatGPT 不是同一件事。

## 本次修复

新进程的 OAuth discovery 缓存为空。此前，程序在请求发现文档之前就写入 `refresh_in_progress`；如果启动后尚未联网或连接失败，即使刷新令牌根本未提交，也会留下永久的刷新不确定标记。下一次启动便要求重新授权。

现在仅在能够确认刷新令牌尚未提交时（发现文档失败、建立连接失败/超时、等待连接池超时）撤销该标记，保留原有凭据，允许网络恢复后再次通过实际请求刷新。读取/写入超时、未知网络错误、未明确拒绝授权的 HTTP 错误响应、异常响应内容和关机中断仍按结果不确定处理，禁止自动重放可能已经轮换的旧令牌。明确的刷新授权拒绝则记录为拒绝并要求重新授权，同样不会重放。

界面区分已有授权但令牌过期、等待刷新窗口、保存的新令牌待验证和刷新结果不确定，避免把正常刷新状态引导为重新授权。

## 已经受影响的账号

不能安全地根据旧 `refresh_in_progress` 标记判断请求是否曾送达上游，因此不会自动删除历史标记。若页面明确显示刷新结果不确定，需要最后手动重新授权一次；修复可避免以后未提交的网络故障再次造成此问题。如果已有待验证的新令牌，应先恢复验证而不是覆盖它。

## 刷新响应验证与诊断

此前 `refresh_in_progress` 与 `login_required` 同时存在时，界面也可能错误显示“刷新结果不确定”；这不能证明发生过网络中断。旧状态未记录具体错误，不能事后断言是哪项验证失败，也不能据此重新使用旧刷新令牌。

现在将刷新失败阶段（请求/验证）、结果分类、白名单错误码、受影响的协议字段名和时间持久化到加密状态；CLI 与控制台仅展示经过白名单过滤的诊断，不记录远端错误描述、令牌或原始响应。验证失败与未知提交结果分开处理，均保持拒绝使用旧凭据。

签名令牌找不到对应 JWKS 公钥时，可能是公钥发布滞后，不能直接判为签名无效。现在保留加密的新凭据，重启后再次手动查询模型时重新获取公钥并验证；验证成功前不允许推理，不再次提交旧刷新令牌。实际签名/声明无效仍拒绝。若身份令牌时间超前，应先校准系统时间再重新授权；不能简单通过稍后校准来改变原始接收时间的验证语义。缺少新的 `refresh_token` 仍视为协议错误，不会回退复用旧令牌。

## 回归覆盖

`tests/test_credentials.py` 覆盖有效/过期凭据重新创建状态存储、离线发现及连接失败后重新启动恢复、已提交请求失败后禁止重放、待验证刷新结果重启恢复。`tests/test_console.py` 区分刷新不确定和待验证状态。浏览器测试覆盖正常令牌过期与等待窗口的界面引导。`tests/test_refresh_diagnostics.py` 覆盖分类持久化、敏感数据过滤与旧标记显示；`tests/test_refresh_recovery.py` 使用模拟传输验证公钥发布滞后后跨重启恢复，刷新 POST 总数严格为一次，以及刷新请求表单和响应省略 scope/id_token 的处理。

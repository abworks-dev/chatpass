## Decisions and readiness

Change Necessity: failed replacement authorization currently invalidates a valid saved account and may overwrite a quarantined refresh successor. Documentation cannot prevent state corruption. Fix the existing credential owner and its login boundary; keep cryptographic and refresh checks intact.

ArchitectureReviewRequired: yes for credential persistence/API state changes; minimum implementation stays in the existing StateStore/Credentials ownership. No duplicate token owner or plaintext migration. Backward compatibility: legacy pending entries with nonce identify login candidates; entries without nonce remain refresh successors. New pending entries may carry an explicit kind. Reject new login while any pending validation exists rather than overwrite it. Validation of a replacement candidate must not mutate the saved account's recovery flags on failure.

Complexity: first slice within budget (Credentials is 88 lines); local fix, edit-in-place, no new module. Subsequent public API/UI changes get scoped readback before edits. Test posture: regression-first where useful, full mock suite/Ruff/whitespace; no strict TDD claim or new dependencies. Security/behavior review before overall completion. No automatic commit because existing interleaved user changes cannot be safely attributed as whole-file task ownership.

## Ordered slices and acceptance

1. **Authorization state isolation (completed).** Invalid/mismatched replacement preserves old credentials, registration, keys and existing recovery flags; pending refresh/login cannot be overwritten; temporary verification outage retains candidate, and an otherwise valid old access token stays usable. New candidates only become authoritative after validation. Cover initial login, legacy pending states, refresh rotation and concurrent behavior.
2. **Logout/revocation (implemented; verification below).** Explicit CLI and authenticated CSRF-protected console action; serialized against login/refresh; revoke via verified official endpoint contract then local cleanup regardless of uncertain remote outcome. Normal logout preserves issued registration, verified subject binding, host and gateway key; only explicit `logout --new-account` / console checkbox resets issued client and subject mapping, preserving host/key, for fresh registration with a different account. Clearly report local logout versus confirmed/unconfirmed/not-needed remote revocation. Do not send predecessor refresh tokens after ambiguous rotation or pending refresh, and do not send unvalidated candidate tokens. Already admitted inference cannot be recalled.
3. **Actionable errors.** Bounded allowlisted status/code/parameter/request ID; no raw remote messages. Distinguish quota, eligibility, transient availability, invalid requests and stream failure; retain no-replay semantics.
4. **Login recovery/plan UI.** Secure short-lived manual authorization URL only in management session; never logs/secrets in status. Hint only from verified encrypted ID token, if protocol/storage evidence supports it. Refresh-window and insufficient-plan-grant states; official usage link and explicit plan consumption warning; no silent billed fallback.
5. **Verification/docs.** Targeted and full local regressions, frontend syntax/browser checks when available, independent security review. Per-client/version user-controlled streaming/nonstream, history, tools, cancellation/error checks. Preserve observed terminal-empty/output-item live gap as a separate acceptance risk rather than quietly assuming it solved.
